# Архитектура ViewTube

Браузер обращается к FastAPI. API обслуживает страницы, проверяет сессии, записывает метаданные в PostgreSQL и передаёт байты в приватный бакет SeaweedFS. Фоновый Python-процесс забирает задания из PostgreSQL и вызывает FFmpeg. Compose публикует только порт API, по умолчанию на loopback. PostgreSQL, S3, bootstrap и worker находятся во внутренней сети.

## Жизненный цикл видео

1. Браузер отправляет исходные байты через XHR. API считает принятые байты, сохраняет поток во временный файл, загружает его в S3 и создаёт запись `queued`.
2. Worker резервирует задание через `FOR UPDATE SKIP LOCKED`, ставит `processing` и записывает идентификатор попытки. После истечения аренды в 45 минут зависшую обработку может взять другой worker.
3. FFprobe проверяет контейнер и длительность. FFmpeg создаёт MP4 H.264/AAC до 720p с `faststart` и JPEG-превью. Обработка ограничена по времени, памяти, формату и разрешённым протоколам. Worker записывает артефакты по ключам, привязанным к попытке.
4. Запись становится `ready`, когда оба файла сохранены и идентификатор попытки в БД совпал. При ошибке worker помечает видео как `failed` и по возможности удаляет файлы незавершённой попытки. Оригинал сохраняется. Владелец может поставить ролик в очередь повторно через интерфейс или `POST /api/videos/{id}/retry`. Публичные ленты выбирают готовые, публичные и нескрытые записи.
5. API проверяет доступ на каждом запросе метаданных, превью и медиабайтов. Поддерживаются GET, HEAD и один диапазон Range, включая суффиксные диапазоны. У ответа `private, no-store`, поэтому после отзыва права браузер повторно обращается к серверу за следующими байтами.

## Схема

- `users` хранит уникальное имя, хеш пароля и роль. Аккаунт одновременно представляет канал.
- `logins` связывает хеш случайного токена с аккаунтом и сроком действия.
- `videos` хранит владельца, заголовок, описание, категорию, видимость, состояние обработки, флаг модерации, длительность и ключи S3.
- `grants` и `likes` связывают видео с пользователем. Составной первичный ключ предотвращает дубли. `comments` связывает видео с автором комментария.
- `subscriptions` связывает канал и подписчика. `playlists` принадлежит владельцу, `playlist_items` связывает плейлист с роликами. При выдаче плейлиста проверяется видимость каждого ролика.
- `reports` хранит причину, статус и модератора, принявшего решение. На пользователя и ролик допускается одна жалоба.

В S3 лежат оригиналы, MP4 и превью. В PostgreSQL лежат связи, задания и данные, необходимые для контроля доступа. Критичные операции используют ограничения уникальности, атомарный SQL-инкремент просмотров и условное обновление по идентификатору попытки.

## Доступ и эксплуатация

Владелец видит свои записи на всех этапах. Остальные видят готовые, нескрытые публичные ролики и готовые приватные ролики с выданным доступом. Модератор и администратор могут принять решение по жалобе. Приватный ролик без разрешения владельца закрыт для обоих. После скрытия владелец сохраняет доступ к собственному видео.

Пароли хешируются scrypt с отдельной солью. Случайный токен сессии хранится у клиента в HttpOnly SameSite=Strict cookie, на сервере хранится его SHA-256. На выходе запись сессии удаляется. Фронтенд вставляет названия и комментарии текстовыми узлами. API проверяет Fetch Metadata для изменяющих запросов из браузера.

Проект рассчитан на один демонстрационный сервер. Для публичного размещения нужны TLS с `SECURE_COOKIES=1`, лимиты запросов на прокси, квоты и резервное копирование томов БД и S3. Возможности для дальнейшего развития включают миграции схемы, адаптивный HLS, повторные попытки при сбоях S3 и сверку объектов с БД для удаления сирот. Уже переданные байты после отзыва доступа остаются у клиента. Счётчик просмотров отражает старты плеера без дедупликации между посещениями.

Использованные источники по развёртыванию: [Docker Engine на Ubuntu](https://docs.docker.com/engine/install/ubuntu/) и [SeaweedFS Quick Start](https://github.com/seaweedfs/seaweedfs#quick-start).
